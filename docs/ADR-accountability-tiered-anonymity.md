# ADR-2610081200 — 説明責任を段階化した匿名性：法域に依存しない分散合意のモデル

Status: **Accepted（R0–R2 実装済み。R3–R5 は未着手）** · 2026-10-08（2026-10-14 に実装状況を反映）
Relates to: ADR-2606112200（Sealed cold tier / `/kotoba/key/1`）、ADR-002（stake-to-replicate）、
ADR-2608180200（Biscuit を委任の中心にする）、`kotoba-protocol/docs/who-may-write.md`、
`kotobase-messenger` の Sealed Sender 相当の実装
Boundary: 本 ADR は、プロトコルの不変条件と、ポリシーを合意する仕組みを定める。
特定の国や地域の法令はプロトコルに埋め込まない。法令は「プロファイル」としてプロトコルの上に接続する（D6, D7）。
暗号方式の選定と実装は、段階（R0–R5）ごとに個別の ADR で決める。

## Context

kotoba は分散型だが、匿名プロトコルではない。設計時点の性質は次のとおり。

- **仮名ではあるが、行為はすべて連結される。** 主体は `did:key`、可変名は鍵から導出される IPNS で、
  「アクターは自分のチェーンにだけ書く」という原則により、行為はすべて一つの DID に紐づく。
- **内容は秘匿できるが、メタデータは見える。** Sealed tier によりブロックは暗号文として複製される。
  一方で、プロバイダーレコード（DHT/IPNI）、メッセージの `toDid`、IP アドレス、鍵要求ログは観測できる。
- **説明責任は、アクセスをすべて記録する方式で担保している。**
  `/kotoba/key/1` は「認証付き・目的宣言付き・受領ログ付き」の鍵要求を前提にしている。

ここで二つの問題がある。

1. **すべてを記録する方式は、監視の基盤になる。** 権力を持つ主体には正しいが、
   一般利用者の閲覧、私的な通信、表現にまで適用すべきではない。
2. **分散型のプロトコルには、単一の法域がない。** 特定の国の法令に合わせて設計すると、
   他の法域では過剰か不足になり、プロトコルがその国の制度の延長になってしまう。

したがって本 ADR は、次の順序で設計する。

> **まず、法域に依存しない「説明責任と匿名性のモデル」を、分散合意で運用できる形で定める。
> 個別の法令は、そのモデルの上に、パラメータの組（プロファイル）として接続してもらう。**

モデルの中心にある命題は次の二つである。

> **説明責任は「人」ではなく「権限」に付ける。
> 匿名を既定とし、悪用した者だけが、暗号的に、自分を開示することになる。**

## 構造：三つの層

```
┌──────────────────────────────────────────────────────────────────┐
│ L2  プロファイル（法域・コミュニティ・業界ごと）                      │
│     閾値、開示を承認できる主体、保存期間、通貨換算 …                   │
│     ↑ L1 のパラメータを埋めるだけ。L0 の不変条件は破れない              │
├──────────────────────────────────────────────────────────────────┤
│ L1  ポリシー（分散合意で決める、内容アドレス付きの署名オブジェクト）      │
│     行為の分類 → 最小 Tier、受託者の集合、パラメータの範囲              │
├──────────────────────────────────────────────────────────────────┤
│ L0  プロトコルの不変条件（暗号で強制する。合意でも変えられない）          │
│     Tier の語彙、開示経路の有無、透明性ログ、遡及の禁止 …              │
└──────────────────────────────────────────────────────────────────┘
```

- **L0 は暗号で強制する。** 合意によって変えられるものを L0 に置いてはならない。
- **L1 は分散合意で決める。** 中央の管理者はいない。ポリシーは CID を持つ署名オブジェクトで、
  各グラフや各コミュニティが、どのポリシーを採用するかを宣言する。
- **L2 は L1 の空欄を埋めるだけ。** 法令はここに接続する。プロファイルは L0 を緩めることができない。

## Decision

### D1. 説明責任は人ではなく、行為の外部性に比例させる（L0）

行為を「他者や社会に及ぼす影響（外部性）」で分類し、行為ごとに**必要な最小の身元の段階（Tier）**を決める。
人そのものに段階を付けるのではない。同じ人が、ある行為では T0、別の行為では T3 で振る舞える。

| Tier | 名称 | 他者から見えるもの | 連結性 | 開示の可能性 |
|---|---|---|---|---|
| **T0** | 匿名 | 資格の証明だけ（例：人間である、会員である、ある年齢以上である） | 行為どうしを連結できない | **経路が存在しない** |
| **T1** | 文脈ごとの仮名 | 文脈ごとのペアワイズ DID と、その文脈での評判 | 同じ文脈の中だけで連結できる | **経路が存在しない** |
| **T2** | 条件付きで開示できる仮名 | T1 と同じ | 同じ文脈の中だけで連結できる | 悪用の証拠があり、独立した k-of-n の受託者が合意したときだけ |
| **T3** | 説明責任を負う主体 | 検証可能な身元（自然人・組織・運営者） | すべて連結される | 常に公開（透明性ログ） |

T3 の「身元」は、特定の国の身分証を意味しない。**L2 のプロファイルが認める資格発行者**が保証する身元である。
国の電子身分証、業界団体の登録、Web of Trust のどれもが発行者になりうる。

### D2. 外部性による行為の分類（L1 の既定値）

分類の基準は法令ではなく、**行為の構造的な性質**に置く。

| 外部性の性質 | 例 | 既定の最小 Tier |
|---|---|---|
| **他者のデータやメタデータを預かる** | インフラの運営（pinning、relay、AppView、鍵ブローカー、アンカーの relayer） | T3 |
| **他者のプライバシーに踏み込む** | 他者の sealed データの鍵を要求する | T3。目的の宣言と受領ログを必須にする |
| **他者の権利を制限する** | モデレーション、アカウントの停止、グラフの検証ルールの変更 | T3。判断理由を公開ログに残す |
| **信頼の根になる** | 資格証明の発行、身元開示の受託者 | T3 |
| **多数に伝播し、取り消せない** | パッケージやコードの公開 | T2。依存の多いものは T3 |
| **価値が他者に移り、取り消せない** | 価値の移転・清算 | 閾値以下は T1、閾値を超えると T2/T3（閾値は L2） |
| **他者の代理として動く** | AI エージェント | 委任の連鎖が T2 以上の主体に行き着くこと |
| **本人の自律の範囲に収まる** | 閲覧、自分のデータの保存と読み出し | T0 |
| **匿名であることが価値の源泉** | 私的な通信、内部告発、秘密投票 | T0 |
| **表現** | 投稿 | T1 |

この表は **L1 の既定値**である。プロファイルは Tier を**上げる**ことはできるが（例：ある業界では価値移転を常に T3 にする）、
L0 の不変条件（D5）に反する変更はできない。

### D3. 匿名のままで悪用を防ぐ仕組み（L0 の暗号的な道具箱）

原則は次の四つ。どれも、特定の誰かの判断や、特定の法制度に依存しない。

- **(a) 資格は証明させるが、身元は明かさせない**
- **(b) 回数と量は制限するが、行為どうしは連結させない**
- **(c) 悪用すると、自分の秘密が漏れるようにする**
- **(d) 匿名主体が持てる権限の大きさに上限を設ける**

| # | 仕組み | 防ぐもの | 原則 | kotoba での接続点 |
|---|---|---|---|---|
| M1 | **匿名資格証明**（BBS+ による選択的開示、ZK 述語） | なりすまし、資格のない参加 | a | 資格発行者（T3）が発行し、Biscuit の third-party block として運ぶ |
| M2 | **文脈ごとの nullifier**（Semaphore 型。`nullifier = H(secret, context)`） | 二重投票、Sybil による水増し | b | 投票、配布、「一人一回」の行為 |
| M3 | **匿名レート制限トークン**（Privacy Pass 型。発行時と使用時を連結できないブラインド署名） | スパム、DoS、スクレイピング | b | gateway / AppView / XRPC の入口 |
| M4 | **RLN（Rate-Limiting Nullifier）**：同じ時間区間で上限を超えて送ると、秘密鍵の Shamir シェアが揃って復元される | 大量送信 | **c** | 復元された鍵で stake を没収し、資格を失効させる。正直な利用者は何も開示しない |
| M5 | **没収可能な stake / bond** | 資源の占有、使い捨てのアカウント | c | ADR-002 の bond を、匿名の預託に一般化する |
| M6 | **権限の上限**（Biscuit による attenuation） | 匿名主体による大きな被害 | d | T0/T1 のトークンには `blast-radius`（対象 CID、操作、期間、量）を必ず付ける |
| M7 | **閾値付きの身元エスクロー**（D4） | 重大な害で身元が必要になる場合 | — | T2 の行為に限る |
| M8 | **Message franking**（E2E を保ったまま、通報されたメッセージだけを検証可能にする） | E2E チャネルでの嫌がらせ | — | kotobase-messenger の sealed 経路 |
| M9 | **受信者が決める到達性**（郵便料金としての PoW、トークン、stake。許可リスト） | 見知らぬ相手からのスパム | b | mailbox ポリシー |
| M10 | **文脈に閉じた評判**（ZK で「評判が閾値以上である」ことだけを示す） | 新規の使い捨てアカウント | a | 文脈を越えて持ち出すときも、連結されないようにする |
| M11 | **違反証拠の gossip**（warrant） | 検証可能な違反の拡散 | — | discovery の warrant gossip（現在はギャップ） |

**最重要の判断は M4/M5 の「悪用すると自分の秘密が漏れる」構造である。**
誰かが判断して身元を暴くのではなく、**規則に違反した行為そのものが、数学的に担保や身元を明かす**。
運営者も合議体も法域も介在しないので、どの法域でも同じように機能し、恣意的な開示も起きない。

### D4. 身元の開示は例外とし、必ず監査できるようにする（L0 の手続き、L1/L2 のパラメータ）

T2 の開示（M7）は最後の手段である。**手続きの形は L0 で固定し、誰が承認できるかは L1/L2 で決める。**

L0 で固定するもの：

1. **閾値暗号**：身元は k-of-n の受託者に分散して預ける。どの単一の主体も開示できない。
2. **受託者の多様性制約**：受託者の集合は、どの一つの法域・組織・運営者も **1/3 を超えて占めてはならない**。
   これにより、一つの国家や企業による強制だけでは開示が成立しない。
3. **証拠に基づく開示**：要求には、対象行為の CID、違反の証拠（warrant）、要求の根拠（承認者の署名）を添える。
4. **透明性ログ**：開示はすべて、追記専用の公開ログに記録する（件数、根拠の種別、日時。対象者の身元は記録しない）。
   ログの head はチェーンにアンカーする。
5. **事後通知**：プロファイルが許す最も早い時点で、開示された本人に通知する。通知を永久に止めることはできない（期限を必ず持つ）。
6. **範囲の限定**：開示されるのは、その文脈の T2 仮名と身元の対応だけ。他の文脈の仮名は連結されない。

L1/L2 で決めるもの：

- k と n の値（L0 は下限だけを定める。例：k ≥ 3、n ≥ 5）
- **要求の根拠として認める承認者の種類**：裁判所の令状、コミュニティの裁定機関、仲裁人など。
  法令による手続きは、承認者の**一種類**として扱う。プロトコルは特定の制度を特別扱いしない。
- 事後通知までの最大期間、ログの保存期間

### D5. L0 の不変条件（合意でも変えられないもの）

1. **T0/T1 には開示の経路が存在しない。** 存在しない経路は、合意でも法令でも強制できない。
2. **遡及の禁止。** ポリシーやプロファイルの変更は、変更後の行為にだけ適用する。
   過去に T0/T1 で行われた行為を、後から T2/T3 に格上げすることはできない（暗号的にも不可能に設計する）。
3. **開示は必ず記録される。** 透明性ログに残らない開示は、プロトコル上の開示ではない。
4. **プロファイルは L0 を一切破れない。** 匿名性を強める方向であっても例外ではない。
   プロファイルが変えられるのは、L1 が開けておいたパラメータと、Tier を上げることだけである。
5. **監視の目は権力の側に向ける。** T3 の主体の行為（他者の鍵の要求、モデレーション、資格の発行、開示）は、
   どのプロファイルでも公開ログに残る。T3 側の記録を減らすプロファイルは無効とする。

### D6. 分散合意によるポリシーの運用（L1）

#### ポリシーはオブジェクトである

ポリシーは、CID を持つ署名付きのオブジェクトとして表現する。中央のレジストリはない。

```edn
{:policy/id        "ipfs://bafy…"                ; 内容アドレス
 :policy/parent    "ipfs://bafy…"                ; 前の版（変更履歴は CID の鎖）
 :policy/l0        "kotoba/accountability/v1"    ; 準拠する不変条件の版
 :policy/effective-from 100                       ; これより前の行為には適用しない
 :policy/actions   {:infra/operate      {:externality :holds-others-data :tier :t3}
                    :value/transfer     {:externality :value-transfer :tier :t1
                                         :escalate {:above :param/value-threshold :to :t3}}
                    :content/post       {:externality :expression :tier :t1}
                    :content/read       {:externality :self-sovereign :tier :t0}}
 :policy/params    {:param/value-threshold {:min 0}
                    :param/disclosure-k    {:min 3}
                    :param/notice-max-days {:min 0 :max 365}}
 :policy/adopted-by #{"did:key:…" …}}            ; 採用を宣言したグラフや運営者
```

#### 誰も「全体のポリシー」を決めない：多中心的な採用

- 各グラフ、各コミュニティ、各運営者は、**どのポリシーを採用するかを宣言する**。
- 異なるポリシーを採用したグラフどうしも、L0 が共通である限り相互運用できる。
- 利用者は、自分が従うポリシーと運営者を**選び、離脱できる**（exit の権利）。ポリシーの正当性は、
  投票ではなく、採用と離脱の自由によって支えられる。

#### 二つのポリシーが交わるときは、厳しい方が勝つ

異なるポリシーの下にある主体どうしが関わる行為では、両方のポリシーの**交わり（meet）**を適用する。
つまり、必要な Tier は高い方、パラメータの範囲は共通部分になる。

これは kotoba の `authority` 束（`covers?` / `meet`）にそのまま対応する。ポリシーの合成は、新しい仕組みではなく、
既存の権限の束の上の演算である。

#### L0 の変更

L0 は合意でも変えられない、と D5 で定めた。ただし暗号方式の更新（例：耐量子化）は必要になる。
L0 の版を上げるときは次を要する。

- 新しい版は、古い版の不変条件をすべて含むこと（不変条件を減らす版は作れない）
- 長い時間的猶予（time-lock）を置き、利用者と運営者が移行するか離脱するかを選べること
- 古い版の下で行われた行為には、古い版が適用され続けること（遡及の禁止）

### D7. 法令の接続（L2 のプロファイル）

法令は、プロトコルを変えるのではなく、**L1 のパラメータを埋めるプロファイル**として接続する。

```edn
{:profile/id          "ipfs://bafy…"
 :profile/policy      "ipfs://bafy…"          ; どの L1 ポリシーの空欄を埋めるか
 :profile/scope       {:kind :jurisdiction :ref "…"}   ; 法域、業界、コミュニティのどれでもよい
 :profile/effective-from 200
 :profile/params      {:param/value-threshold 1000
                       :param/notice-max-days 90}
 :profile/authorizers [{:kind :court-order :issuer-set "…"}
                       {:kind :community-tribunal :issuer-set "…"}]
 :profile/credential-issuers #{"did:key:…"}  ; T3 の身元を保証できる発行者
 :profile/tier-raises {:code/publish :t3}}    ; Tier を上げる（下げることはできない）
```

**法令の義務は、T3 の境界で引き受ける。** 法令が義務を課す相手は、ほとんどの場合、
運営者・金融事業者・プラットフォームといった**権力を持つ主体**である。これらはすでに T3 なので、
法令への対応は T3 の運営者がプロファイルを採用することで行う。T0/T1 の利用者の側に、
法令ごとの仕組みを持ち込む必要はない。

プロファイルにできないこと：

- T0/T1 に開示の経路を作ること（D5-1）
- 受託者の多様性制約を外すこと（D4-2）
- 過去の行為に遡って適用すること（D5-2）
- T3 側の記録を減らすこと（D5-5）

ある法令が、これらを要求する場合は、**その法域の運営者がそのプロファイルを採用できない**という結果になる。
プロトコルは、その法令に合わせて変わらない。これが、分散型のプロトコルが特定の法域の延長にならないための境界である。

## 既存設計への適用

| 箇所 | 当初 | 変更の方向 | 状態 |
|---|---|---|---|
| 主体（`did:key`） | 主体ごとに単一の鍵 | 一つのルート鍵から、文脈ごとのペアワイズ DID を導出する（T1） | 仕様は R1 で実装。鍵の導出は org-ietf-ed25519 側 |
| 認可（`authority` / Biscuit） | 権限の範囲だけを扱う | `:cap/tier` と `:cap/blast-radius` を `lang/capability-semantics.edn` に追加する。ポリシーの合成を `meet` で行う | 合成は R1 で実装。`capability-semantics.edn` への追加は未着手 |
| `kotoba.protocol.govern/decide` | 自分のグラフへの CACAO self-mint だけ | 採用しているポリシー（とプロファイル）から必要な Tier を引き、満たさない intent を拒否する | R0 で実装 |
| Sealed tier / `/kotoba/key/1` | すべての鍵要求を記録する | 自分の鍵で自分のデータを読むときの記録は本人のみが見られるようにし、他者のデータへのアクセスは運営者にも見えるまま記録する | R1 で実装（kotoba-server#3）。記録自体は残す。custodian の記録漏れ監査を保つため |
| メッセンジャー | `toDid` が平文 | セッションの2通目以降は、セッション鍵から導出した不透明な mailbox ID で宛先を置き換える | R1 で実装（kotobase-messenger#5）。最初の1通は従来どおり |
| プロバイダーレコード | 利用者のピアが広告される | 利用者は T3 の pinning 運営者に匿名トークンで預け、広告は運営者の名義で行う | 未着手 |
| トランスポート | Tor は表現できるだけ | T0 の行為には relay / Tor を経由するモードを用意する（IP アドレスを隠す） | 未着手 |
| ADR-002 の stake | 複製者の bond | 匿名の預託（M5）と RLN による没収（M4）に一般化する | 未着手（R4） |
| 価値の単位 | — | プロトコル内の単位（`:kotoba/value-unit`）で閾値を表し、通貨への換算はプロファイルが行う | 未着手 |

## Phases

| 段階 | 内容 | 依存 | 状態 |
|---|---|---|---|
| **R0** | L0 の不変条件と Tier の語彙を EDN で定める。L1 ポリシーと L2 プロファイルのスキーマを定める。`decide` で Tier の不足を拒否する（暗号はまだ使わない） | なし | 完了（kotoba-protocol#5） |
| **R1** | ペアワイズ DID、メッセンジャーの mailbox ID、自分のデータを読むときの受領記録、ポリシーの `meet` による合成 | R0 | 完了（kotoba-protocol#7、kotobase-messenger#5、kotoba-server#3） |
| **R2** | 匿名レート制限トークン（M3）。発行者と検証者を分ける | R0 | プロトコル側の代数は実装済み（kotoba-protocol#12）。ブラインド署名の実装と gateway / XRPC への組み込みは未着手 |
| **R3** | BBS+ による資格証明（M1）と、文脈ごとの nullifier（M2） | R2 | 未着手 |
| **R4** | RLN（M4）と、匿名の stake（M5） | R3、ADR-002 | 未着手 |
| **R5** | 閾値付き身元エスクローと透明性ログ（D4）、受託者の多様性制約の検証。message franking（M8） | R3 | 一部実装（受託者の多様性制約と開示要求の検査は R0 で実装済み。閾値暗号の実体と透明性ログは未着手） |

## R1 で判明したこと

- **本人のアクセスの判定は、検証済みの署名者に基づく。** 検証されていない申告や、委任チェーンの根の発行者を使うと、
  委任された第三者の読み出しまで「本人のみ」に分類される。kotoba-server#3 のレビューで修正された。
- **mailbox ID は、セッションを確立する最初の1通には使えない。** 受信者は、その1通を復号するまで ID を計算できない。
  最初の1通は従来どおり宛先が見える。
- **会話 ID も秘匿しなければ、宛先を隠した意味がない。** 会話の記録はメンバー一覧を公開しているため、
  平文の `convoId` から宛先が逆算できる。mailbox 経由のメッセージでは、`convoId` を暗号文の中に移した。
- **「本人のみ」の受領記録は、運営者向けの一覧から外しただけである。** 運営者の監査グラフには平文で残っている。
  本人の鍵で暗号化するのが次の段階である。

## Consequences

**得られるもの**

- プロトコルは特定の法域の延長にならない。どの法域の運営者も、同じ L0 の上でプロファイルを採用して参加できる。
- 一般利用者の行為の大半（閲覧、保存、通信、表現）が、監視の対象から外れる。
- 悪用の抑止を「誰かの判断」ではなく「暗号的な帰結」に移せるので、どの法域でも同じように働き、恣意的な開示も起きない。
- 説明責任は、権力を持つ少数の主体に集中する。法令が義務を課す相手と、プロトコルが説明責任を課す相手が一致する。

**引き受ける代償**

- 暗号方式（BBS+、ZK、RLN）の実装と監査のコスト。ブラウザや WASM での証明生成の性能。
- 匿名性は**最も弱い層で決まる**。トランスポート、タイミング、ペイロードの形のどれかが漏れれば、上位の匿名性は崩れる。
- T0 の領域では、事後の捜査がほぼ不可能になる。これは仕様であり、社会的な説明が必要になる。
- 一部の法域では、運営者が L0 と両立するプロファイルを採用できない可能性がある。その法域では、kotoba の運営者として参加できない。
- 受託者の選び方と、ポリシーの採用の仕組みは、技術ではなくガバナンスの問題であり続ける。

## 脅威と、その対策

| 脅威 | 対策 |
|---|---|
| 運営者が利用者を連結する | トークン発行者と検証者の分離、ペアワイズ DID、データ最小化の公開と監査 |
| 一つの国家による強制での大量開示 | T0/T1 には開示経路がない。T2 は受託者の多様性制約により、一つの法域だけでは開示が成立しない。透明性ログとカナリア |
| 受託者の結託 | 法域と組織の多様性制約。開示は透明性ログに必ず残る |
| ポリシーの乗っ取り（悪意あるポリシーの普及） | L0 は変えられない。利用者は離脱できる。交わりでは厳しい方が勝つ |
| 資格発行者の誤発行・不正発行 | 発行者は T3。発行ログを公開する。資格を失効できるようにする。プロファイルごとに発行者を選べる |
| Sybil（資格の大量取得） | 発行時の本人確認。文脈ごとの nullifier。stake |
| 使い捨ての仮名 | 評判と stake により、新しい仮名ほど権限が小さくなる |
| AI エージェントの大量行動 | エージェントにも RLN とトークンを適用する。委任の連鎖が説明責任のある主体に行き着くことを要求する |
| 規制の緩い法域への運営者の移動（規制逃れ） | T3 の行為は、どのプロファイルでも公開ログに残る（D5-5）。他のポリシーとの交わりでは厳しい方が勝つ |
| 発行者と検証者の結託によるトークンの連結 | 発行者と origin を、鍵と組織の両方で分離する。発行ログと使用ログが、epoch と鍵 ID 以外の項目を共有してはならない |

## Open questions

1. L0 の不変条件の最小の集合はどれか。多すぎると採用されず、少なすぎると守れない。
2. 受託者の多様性制約で、「法域」「組織」をどう検証可能に定義するか。自己申告では足りない。
3. ポリシーの採用を宣言する主体の重み。グラフの数か、利用者の数か、stake か。それとも重みを付けずに、交わりだけで扱うか。
4. 価値の単位（`:kotoba/value-unit`）をどう定義するか。プロファイルの通貨換算の基準をどこに置くか。
5. 証明生成の性能。モバイルや WASM で、RLN と BBS+ の証明が実用的な時間で生成できるか。
6. 文脈（context）の粒度。細かすぎると評判が育たず、粗すぎると連結性が高まる。
7. 「本人のみ」の受領記録を、本人の鍵で暗号化して運営者から読めなくするとき、custodian の記録漏れ監査との両立をどう保つか。

## 付録：プロファイルへの法令の写像の例

以下は、L2 のプロファイルに法令がどう写るかの**例**である。プロトコルの一部ではなく、法的な助言でもない。
各法域の運営者が、専門家の確認のうえでプロファイルを作成する。

| 法令の類型 | 写る先 | 例 |
|---|---|---|
| 送金・決済の本人確認（AML/KYC） | `:param/value-threshold`、`:profile/credential-issuers` | 閾値を超える価値の移転を T3 にし、認められた本人確認業者を資格発行者にする |
| 発信者情報の開示請求 | `:profile/authorizers` | 裁判所の命令を承認者に加える。対象は T2 の行為だけで、T1 には経路がない |
| 通信の秘密 | D5（L0）と整合するかの確認 | 運営者が通信の内容とメタデータを持たない設計は、多くの場合この類型と整合する |
| データ保護（目的の限定、保存期間、本人の権利） | `:param/notice-max-days`、ログの保存期間、データ最小化 | 運営者の保持するデータの種類と期間を公開する |
| サプライチェーンの責任 | `:profile/tier-raises` | コードの公開を T3 に上げる |
