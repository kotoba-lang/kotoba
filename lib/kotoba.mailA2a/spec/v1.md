# MailA2A Binding 1.0

Status: Experimental community specification  
Updated: 2026-08-30  
Binding URI: `https://kotoba-lang.github.io/mail-a2a/spec/v1/`  
A2A protocol version: 1.0  
License: Apache-2.0

The key words **MUST**, **MUST NOT**, **REQUIRED**, **SHOULD**, **SHOULD NOT**,
and **MAY** are to be interpreted as described by BCP 14 when they appear in
all capitals.

## 1. Scope

MailA2A is a store-and-forward custom binding of the A2A v1.0 abstract
operations and data model to Internet email. An RFC 5322 message is one request,
response, error, or stream event. MIME carries the protected A2A JSON document,
human fallback, binary parts, optional end-to-end security, x402 v2 objects,
and MLS messages.

The binding does not change A2A task semantics. SMTP acceptance, a delivery
status notification, or an IMAP `\Seen` flag is never an A2A success result.

## 2. Design requirements

1. Reuse A2A v1.0 objects and task states without inventing a parallel agent
   language.
2. Work through ordinary standards-conforming mail servers and provider APIs.
3. Be asynchronous by default; never pretend email provides low-latency SSE.
4. Keep authoritative metadata inside the signed or encrypted MIME subtree.
5. Make duplicate delivery, reordering, delayed delivery, and replay explicit.
6. Reuse exact x402 v2 objects and exact MLS wire messages.
7. Permit a human-readable part without allowing it to override machine data.

## 3. Discovery and Agent Card

An agent continues to publish its Agent Card at the A2A well-known HTTPS URI.
It advertises MailA2A as an additional interface:

```json
{
  "supportedInterfaces": [{
    "url": "mailto:research-bot@example.com",
    "protocolBinding": "https://kotoba-lang.github.io/mail-a2a/spec/v1/",
    "protocolVersion": "1.0"
  }],
  "capabilities": {
    "streaming": true,
    "pushNotifications": false
  }
}
```

`url` MUST be a `mailto:` URI with one addr-spec and no pre-filled body.
Discovery of the mailbox does not authorize a sender. Security schemes and
policy in the Agent Card remain authoritative. A deployment MAY publish a
JWS-signed Agent Card.

Because the current A2A schema text describes endpoint URLs mainly in terms of
network URLs, official adoption may require clarification that `mailto:` is a
valid endpoint URI for a custom binding. Until then an implementation MUST call
it "MailA2A-compatible", not an official A2A binding.

## 4. Message shape

### 4.1 Internet message

Every protocol message MUST have:

- valid `From`, `To`, `Date`, and globally unique `Message-ID` fields;
- `MIME-Version: 1.0`;
- a machine part with `Content-Type: application/a2a+json`;
- a UTF-8 JSON object conforming to `schema/envelope-v1.schema.json`;
- a `Mail-A2A-Binding: 1.0` routing hint.

Responses and events MUST include `In-Reply-To` referencing the request's RFC
5322 `Message-ID`, and SHOULD carry the thread chain in `References`.

The following unregistered `Mail-A2A-*` fields are experimental routing hints:

| field | value |
|---|---|
| `Mail-A2A-Binding` | `1.0` |
| `Mail-A2A-Operation` | operation token from section 5 |
| `Mail-A2A-Kind` | `request`, `response`, `event`, or `error` |
| `Mail-A2A-Correlation-ID` | opaque identifier shared by one operation exchange |
| `Mail-A2A-Sequence` | unsigned decimal event sequence |
| `Mail-A2A-Final` | `yes` or `no` |

Receivers MUST NOT authorize, pay, execute tools, or advance task state from
these outer fields alone. Their protected-envelope counterparts are
authoritative. A mismatch is `InvalidRequestError`.

### 4.2 Protected envelope

The `application/a2a+json` part contains:

```json
{
  "bindingVersion": "1.0",
  "a2aVersion": "1.0",
  "kind": "request",
  "operation": "message/send",
  "messageId": "018f...",
  "correlationId": "018f...",
  "taskId": null,
  "contextId": null,
  "sequence": 0,
  "final": false,
  "createdAt": "2026-08-30T07:00:00Z",
  "expiresAt": "2026-08-31T07:00:00Z",
  "idempotencyKey": "018f...",
  "serviceParameters": {"traceparent": "..."},
  "payload": {"message": {"messageId": "018f...", "role": "ROLE_USER", "parts": []}}
}
```

Field names inside `payload` use the canonical A2A JSON mapping. Timestamps are
RFC 3339 UTC strings. Binary A2A `bytes` values use canonical padded base64.
Enums use the canonical symbolic names. Unknown envelope fields MUST be
preserved by relays and ignored by older implementations unless a declared
extension says otherwise.

`messageId` identifies this MailA2A protocol message and is distinct from the
RFC 5322 `Message-ID`. `correlationId` identifies the operation exchange.
`idempotencyKey` is REQUIRED for effectful operations.

### 4.3 MIME attachments and A2A Parts

An A2A `FilePart` MAY be inline in JSON or externalized as a sibling MIME part.
An externalized part MUST have a unique `Content-ID`; the A2A `FilePart.uri`
then uses the corresponding RFC 2392 `cid:` URI. The declared media type and
digest MUST match before the part is exposed to an agent.

A `text/plain; charset=utf-8` human fallback MAY be included. It is informative
only and MUST NOT be concatenated with, substituted for, or treated as
instructions extending the protected A2A payload.

## 5. Operation mapping

Each A2A operation maps to `operation` and the same canonical request/response
object in `payload`:

| A2A operation | MailA2A token | response pattern |
|---|---|---|
| Send Message | `message/send` | one response or ordered task events |
| Send Streaming Message | `message/stream` | ordered events, one final event |
| Get Task | `tasks/get` | one Task response |
| List Tasks | `tasks/list` | one ListTasksResponse |
| Cancel Task | `tasks/cancel` | one Task response |
| Subscribe to Task | `tasks/subscribe` | ordered events until final/unsubscribe |
| Create Push Config | `push/create` | one TaskPushNotificationConfig |
| Get Push Config | `push/get` | one TaskPushNotificationConfig |
| List Push Configs | `push/list` | one list response |
| Delete Push Config | `push/delete` | one empty success response |
| Get Extended Agent Card | `agent-card/get-extended` | one AgentCard response |

Mail itself normally supplies asynchronous updates, so deployments SHOULD set
`pushNotifications: false`. If enabled, push configuration and authentication
retain A2A semantics; the callback endpoint MAY use another declared binding.

## 6. Streaming, ordering, and recovery

Email streaming is a finite ordered sequence of messages, not a live byte
stream. For one correlation ID:

- the request has `sequence: 0`;
- response/event sequence numbers increase by exactly one;
- exactly one message has `final: true`;
- duplicates with the same message ID and identical protected bytes are
  ignored; same ID with different bytes is a security error;
- a gap or reorder MUST pause delivery to the agent until the missing event is
  obtained or the task is refreshed with `tasks/get`;
- terminal Task states require `final: true`.

An implementation MAY buffer out-of-order messages within a published bound.
It MUST expose expiry and incomplete-stream state rather than silently joining
around a gap.

## 7. Idempotency and replay

Receivers MUST persist a replay tuple of authenticated sender identity,
`messageId`, `idempotencyKey`, operation, and protected-content digest for at
least the accepted message lifetime. Messages past `expiresAt` are rejected.
SMTP redelivery of identical bytes is not a second operation.

Retries keep `idempotencyKey` and correlation ID, use a new RFC 5322
`Message-ID`, and increment an optional retry counter in `serviceParameters`.
A payment retry additionally carries section 8's `PaymentPayload`.

## 8. x402 v2 payment profile

x402 v2 data structures are transport-neutral. MailA2A maps them without
changing field names or payment-scheme validation:

1. The receiver returns `kind: "error"`, `error.type:
   "PaymentRequiredError"`, and exact `PaymentRequired` under
   `payment.object`, with `payment.kind: "required"`.
2. The sender retries the original operation with the same idempotency key and
   exact `PaymentPayload` under `payment.object`, with `payment.kind:
   "payload"`.
3. The receiver verifies or settles using the selected x402 scheme and returns
   exact `SettlementResponse` under `payment.object`, with `payment.kind:
   "response"`.

The MailA2A payment wrapper has `x402Version: 2`. `PaymentRequired` and
`PaymentPayload` retain their required `x402Version: 2`; `SettlementResponse`
is carried exactly as x402 defines it and does not gain that field. The HTTP status and
`PAYMENT-REQUIRED`, `PAYMENT-SIGNATURE`, and `PAYMENT-RESPONSE` headers are not
copied into email headers. `PaymentRequired.resource.url` SHOULD be an HTTPS
task/resource URL; when no web resource exists it MAY be the RFC 2392 `mid:` URI
of the protected request.

The payment object authorizes only the named resource and amount. It never
authorizes unrelated agent tools, later messages, group membership, or budget
increases. A mailbox or relay MUST NOT receive wallet keys.

## 9. Security profiles

### 9.1 Baseline transport

SMTP TLS protects hops, not message content end to end. SPF, DKIM, DMARC, and
ARC are useful domain and transit signals but do not establish agent-level
authorization. A receiver MUST authenticate the protected content before any
effectful operation.

### 9.2 Direct messages

The Agent Card declares one of:

- `smime-4`: S/MIME 4.0 signed or signed-and-encrypted MIME;
- `openpgp-mime`: OpenPGP/MIME signed or signed-and-encrypted MIME;
- `detached-jws`: a JWS over canonical protected JSON for non-confidential
  messages.

Confidential mode MUST provide authentication and integrity as well as
encryption. Header protection conforming to RFC 9787/RFC 9788 SHOULD be used;
otherwise every security-relevant value remains inside the cryptographic
envelope and outer fields are treated only as hints.

Agent identity binding to a certificate, OpenPGP fingerprint, DID, or JWK is a
deployment policy and MUST be declared. Email address equality alone is not a
cryptographic identity proof.

### 9.3 Groups

Private groups MUST carry the protected MailA2A envelope as MLS application
data inside an RFC 9420 `message/mls; version=1.0` MIME part. The outer list or
mail server distributes identical opaque MLS bytes and is not trusted with
plaintext.

MLS epoch and generation are the cryptographic ordering authority. MailA2A
sequence is the A2A application ordering authority. Membership changes use MLS
Proposal, Commit, Welcome, KeyPackage, and GroupInfo messages; adding an email
recipient without an accepted MLS commit does not add a group member.

S/MIME or OpenPGP encryption separately to a static recipient list MAY be used
for small direct fan-out but MUST NOT be described as the MLS group profile: it
does not provide MLS forward secrecy or post-compromise security.

## 10. Error mapping

Errors use `kind: "error"` and an A2A error object in `error`. The correlation
ID and operation match the request. Mail transport errors remain DSNs and do
not masquerade as A2A errors.

| A2A error | mail behavior |
|---|---|
| `InvalidRequestError` | malformed envelope, MIME mismatch, invalid fields |
| `MethodNotFoundError` | unknown operation token |
| `InvalidParamsError` | valid operation with invalid payload |
| `TaskNotFoundError` | inaccessible or absent task |
| `TaskNotCancelableError` | task cannot be canceled |
| `PushNotificationNotSupportedError` | push is disabled |
| `UnsupportedOperationError` | declared capability does not support operation |
| `ContentTypeNotSupportedError` | unacceptable A2A Part media type |
| `InvalidAgentResponseError` | peer returned a nonconforming response |
| `ExtendedAgentCardNotConfiguredError` | extended card declared but absent |
| `ExtensionSupportRequiredError` | required extension was not negotiated |
| `VersionNotSupportedError` | A2A or binding version unsupported |

`PaymentRequiredError` is a MailA2A extension error carrying section 8's x402
object. It does not replace any A2A core error.

## 11. Resource and abuse limits

Agent Cards SHOULD publish maximum decoded message size, MIME part count,
attachment size, history length, buffered reorder window, expiry horizon, and
messages per sender per interval. Receivers MUST validate decompressed size,
MIME nesting depth, content digests, URL schemes, and file references before
agent exposure. Automatic replies MUST have loop detection and a finite retry
budget.

Unsolicited email is untrusted input. A valid DKIM signature or valid end-to-end
signature is not authority to execute arbitrary instructions. Authorization is
evaluated against agent policy, task, sender, scope, expiry, and budget.

## 12. Conformance

A MailA2A implementation conforms to binding 1.0 only if it:

1. preserves A2A v1.0 operation and data semantics;
2. emits and validates the protected envelope and RFC 5322 correlation fields;
3. implements deduplication, expiry, idempotency, sequence, gap, and finality
   rules;
4. never treats transport delivery as task completion;
5. authenticates protected content before effectful processing;
6. maps all implemented A2A operations and all A2A errors explicitly;
7. passes the published examples and reference-validator tests;
8. labels unsupported optional capabilities accurately in its Agent Card;
9. preserves exact x402 v2 objects without adding or renaming fields; and
10. for private groups, uses MLS rather than claiming static fan-out is MLS.

## 13. Privacy considerations

Email necessarily exposes routing metadata to mailbox operators. Even with MLS,
message frequency, sender/recipient addresses, size, and timing can leak. Group
aliases can additionally reveal membership. Implementations SHOULD minimize
outer Subject text, use opaque correlation IDs, apply padding where useful, and
avoid including task descriptions in routing headers.

## 14. Non-goals

MailA2A does not standardize mailbox provisioning, spam reputation, wallet key
custody, payment settlement schemes, MLS cipher suites, legal electronic
signatures, human consent, or agent governance. It does not claim real-time
latency and does not make SMTP a replacement for the A2A HTTP bindings.

## Appendix A. Minimal exchange

```text
Client mailbox                     Agent mailbox
     |                                  |
     | message/send, seq=0              |
     |--------------------------------->|
     |  working Task, seq=1             |
     |<---------------------------------|
     |  artifact update, seq=2          |
     |<---------------------------------|
     |  completed Task, seq=3, final    |
     |<---------------------------------|
```

If sequence 2 is missing, the client does not deliver sequence 3 as a complete
stream; it sends `tasks/get` or waits within its advertised reorder window.
