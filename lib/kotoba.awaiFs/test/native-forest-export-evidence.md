# Cooperative Native Forest export, 2026-11-14

`forest-export/export-new` holds the existing local cooperative writer lock while `forest-head/recover-held` parses HEAD and verifies the caller-supplied CID and generation. It rereads and validates the manifest, checks every returned chunk against its CID, writes into a fresh private directory, syncs the file and directory, and publishes with no-replace rename followed by directory sync. Output names are restricted to `file-` followed by lowercase letters, digits or hyphens. Failed stages remain for inspection. A status 112 rename failure can include a malformed response; status 113 after rename or status 102 on unlock means outcome may be uncertain. A provider trap can terminate the process.

On the dedicated Ubuntu 26.10 aarch64 guest, the Native smoke exported a one-byte generation and its output matched the source by `cmp` and SHA-256 `22adaf058a2cb668b15cb4c1f30e7cc720bbe38c146544169db35fbf630389c4`. Repeating into the existing destination returned 112 and left the bytes intact; wrong expected CID returned 105 and did not publish; invalid name returned 1. Artifact and guest source-lock SHA-256 were `c64e940b764e1f98801707d9b14769f7112ccd9cd5e13da73df7136e7660633e` and `fdaad2ef6423ddb5ceec5d85195500e304cfb9701223851792d2678dbec63a63`.

While a separate process held the stable writer flock, the two-Pack artifact returned busy status 104 without creating the destination. This verifies lock contention refusal, not hostile-writer protection.

For a separate task-owned two-Pack copy, the uninstrumented Native export process was SIGKILLed after a private staged file reached 1,048,576 bytes. The final destination did not exist, the partial stage remained, and a fresh process acquired the writer flock. A fresh run of the same artifact published the output; `cmp` and SHA-256 matched the 16,777,219-byte source. Artifact and source-lock hashes were `25dc7ada9614615eb8a83717c175e0fcc3ba9ec0dbbf1ff881344e614e0e2c3a` and `03fde336f83be065a758c68d50f09aa370876ba22df036bec966c25e78804b1a`. This is one process-kill point before rename; it does not establish post-rename crash, cache-loss or power-loss behavior.

The gate passed on the dedicated guest; the artifact and source-lock hashes were `2f4ba025a22e9acc4ea5898a737064a6642d072ee303694fc2ae514571bc6573` and `8681344d1630e32ff1aacf9c4ab842697e2fc8f941f5e6a47a98d30f22305590`. Its artifact and lock hashes were `f4e48b3ac247bbfd3186c1b5f7707ed512d84ea30cea962409edb402d73ebea2` and `0b674179c89f9da1db685471adca6f380bc84c4601ab526a2ab9e72446230e38`. The actual `export-new` API was then exercised on the earlier clean-reboot 1 GiB generation (1,024 chunks / 64 Packs), using `native_forest_export_gib.kotoba`. It returned `:status :ok :result 0`, published exactly 1,073,741,824 bytes, and the output matched the input by `cmp` and SHA-256 `f0add2045c361a831c9298f69c09e65a79c0c83d38bc97bc84bfe9b909dc5d77`. The API call ran 794 seconds (about 1.35 MB/s of logical output), including initial HEAD/generation verification, staged writes, sync and no-replace publication, but excluding compilation and subsequent `cmp`/hashing. The mostly-zero synthetic input, prior reads, warm guest/host caches and single sample preclude general performance conclusions. Artifact and source-lock SHA-256 were `bf96695179b8ca4900b496b41c539e7a68159f7ab95427f68b6ab8fad16a79c5` and `667856534f14465bed568ae128a93712da2f27ade9c433887294f0c7a8e4697e`.

This is a bounded library primitive, not a product-runtime integration or a signed-authority implementation. The caller authenticates the expected CID, and all local writers and collectors must use the same stable lock inode; same-identity interference, concurrent noncooperating mutation and provider traps are not excluded. It does not provide WAL replay, rollback protection, hostile or distributed fencing, automatic orphan cleanup, exhaustive crash-point qualification or physical power-loss proof.
