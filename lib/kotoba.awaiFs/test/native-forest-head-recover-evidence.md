# Native Forest HEAD recovery with expected CID, 2026-11-14

`forest-head/recover` takes a parent directory and a caller-supplied expected manifest CID. Under the same cooperative local writer lock, it reads at most 256 bytes of HEAD, rejects non-ASCII or malformed management records, validates the generation name and CID, compares that CID to the externally supplied value, and verifies every referenced chunk of that generation. It returns the observed name and CID only on success. It does not scan or fall back to another generation. Status 105 covers missing, malformed or unexpected HEAD; 106 means the referenced generation failed verification; 104 means busy. Some provider errors can trap. The lock covers this observation only and does not preserve a snapshot after return.

In the dedicated Ubuntu 26.10 Linux aarch64 guest, the pinned Native compiler built `native_forest_head_recover_smoke.kotoba` for a copy of the prior two-Pack HEAD. It recovered `gen-a` with the expected CID and rejected a different valid CID. In a separate status fixture, a malformed short HEAD, non-ASCII byte and trailing newline each returned 105. A corrupted or withheld Pack of the referenced generation returned 106; HEAD was not rewritten and a second generation remained present throughout. The test restored its own modified files.

After guest `sync`, clean shutdown and restart, boot ID changed from `eefd39be-05cd-40eb-88a3-7805d9724ee0` to `82a7f5d5-b708-4e69-ad06-0a60c6298539`. The same Native artifact parsed HEAD and verified the generation successfully; artifact SHA-256 `aba1a2dba0ed61352ebd205fc33ced574603e4927230b7ef3f2ea3f87f20fc56`, guest-specific source lock `ca5f0bc0b4184dec47ed086d7c8b61bbb72af369f6133675054e4271c6cdddec`, and HEAD SHA-256 `49defbe389615a2c4448213810607e2fa71538573e06d9e4907ac4c363d7c7d4`. Inputs and outputs remain in the task-owned guest.

The expected CID is not authenticated here. Signed basis and key authority, durable anti-rollback state, uncooperative writer protection, WAL replay, safe orphan cleanup, actual I/O failures and physical power-loss qualification remain open. This is a clean guest reboot with host caches uncontrolled, not proof of a hardware power cut.
