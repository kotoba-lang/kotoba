# Native CID-checked generation publication, 2026-11-14

`forest-verified-publish/publish` creates and syncs private staging, checks its canonical logical manifest and every referenced chunk against a caller-supplied expected manifest CID, and only then publishes the directory through Linux FS2 T no-replace rename and syncs the parent. Status 101 means generation verification failed and returns the staging path. Status 95 means rename returned false and retains the staging path; 96 means rename succeeded but the final parent sync failed, so the target may already be visible; 97 means the response was malformed and publication state is unknown. Provider traps may terminate the process without returning a status. The caller supplies and must authenticate the CID.

On the dedicated Ubuntu 26.10 aarch64 guest, the pinned Native compiler built `native_forest_verified_publish_smoke.kotoba` for a 16,777,219-byte / two-Pack source. An incorrect CID returned 101 and created no `gen-bad`. The correct CID `bafyreifofrzrmfqc2affepxac6oyi57owuaulr3pvmqi2dftdtfmjtxifq` returned 0, and its Pack and manifest bytes matched the independently validated earlier generation. Native artifact SHA-256 `4c83a1b0ce032bbfc28ccb84c18a3ebf5eae78c9493f33b42f80aa5140efa23a`; guest-specific source lock `27912f1be88d1def62caeb72383da70a0dc0e219e27d2c2d63f9695daf5bf054`. A second build using `native_forest_verified_publish_collision.kotoba` returned 95 for the existing name and preserved the published bytes.

A separate test-only source-instrumented build paused after staging and before verification. The observer altered a byte of staging Pack 1, then released the barrier. The Native process returned 101 and `gen-test` was absent. Instrumented module SHA-256 `753c05657202e3a905674755f766a43dbefc0bac14f2e21138b75ce26a235b14`; instrumented artifact `8ac27159f1fdb673139c344050143132bc1d15cd53319afbca55a3b91d2aa806`. This is an injected test, not a hostile concurrency qualification.

No signature or authorization check is performed, and the source or staging files can change between checks and rename. Existing directories may be tampered with by the same identity; partial or rejected staging is retained. WAL, mutable head updates, writer fencing, orphan cleanup, real I/O error handling and physical power-loss guarantees remain open. Native inputs and logs remain in the dedicated guest; the test barrier source is retained in `.agent-output/native-verified-publish-control` and is not in the production path.
