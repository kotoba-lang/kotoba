# Native full candidate search over the actual Otehon 1 GiB

On 2026-11-14 Darwin 25.4.0 arm64, the opt-in `NATIVE_GIB_SEARCH_ALL=1` mode used the actual Otehon-generated 1 GiB manifest and 64 Forest files described in `actual-gib-native-evidence.md`. Unlike the earlier fixture-selected single Pack per chunk, `forest_gib_search.kotoba` supplies all 64 ordered paths and sizes to the existing `forest-view/read-chunk` for each of 1,024 chunks. Native selects candidate archives with `forest-file/get-block-in-files`; it validates each returned block CID and length and the whole-stream SHA-256 `1f7e0c0d3fefe5579e556a04f7796b7de01278916e49a6d31df864e16adf1708`. The test does not provide a chunk-to-Pack mapping, although the ordered candidate list and file sizes are supplied test inputs.

The final Python-free shell gate returned positive 0, staged Pack 31 corruption 41 and staged Pack 31 missing 41; all three stderr streams were empty. The signed Native executable SHA-256 was `01c5339711359c2b3cc45cef620b87e75492df354a730334749ae3de5fcee45c`; its KSL1 source lock SHA-256 was `55df4a5f14bda279edc2b8685af6610674852c48efda7beb6f249ba450d3cef6`. A single `/usr/bin/time -l` run including input staging, compilation, positive and both negative cases took 158.10 s and reported maximum RSS 254,771,200 bytes. The host cache, scheduling and workload were uncontrolled; this is not an isolated read or comparative performance benchmark.

The data are highly compressible synthetic bytes; the Otehon-hosted one-off extraction and pinned Pack list remain as described in the earlier evidence. This demonstrates local macOS Native multi-file candidate search and failure propagation, not an authenticated persistent catalog or a proof that an index miss means absence. It does not qualify Linux, Native writing/root publication, OS cache-loss recovery, physical device failure, distributed storage or production. The old broader Python-based workflow and exact-head CI remain separate unresolved issues.
