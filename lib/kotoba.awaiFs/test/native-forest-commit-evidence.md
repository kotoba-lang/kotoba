# Native cooperative Forest generation and HEAD commit, 2026-11-14

`forest-commit/commit` holds the scoped local writer flock while it checks the caller's expected old HEAD and referenced generation, stages and verifies a source against the caller-supplied new CID, publishes the new generation without replacement, rechecks the old HEAD and verifies the new generation, then atomically advances HEAD. An already-existing generation is accepted only after verifying its manifest CID and every expected chunk; name equality alone is insufficient. On a failed operation, staged data or an unattached generation can remain. Return statuses inherit the publication and HEAD APIs; unlock failure is outcome-uncertain. `forest-head/check-held` and `advance-held` are low-level composition hooks requiring the caller to hold the same lock; calling them without it is unsafe.

On the dedicated Ubuntu 26.10 Linux aarch64 guest, the pinned Native compiler ran `native_forest_commit_smoke.kotoba`: bootstrap from a 16,777,219-byte / two-Pack source and update to a one-byte source both succeeded, stale preconditions returned 105, and HEAD recovery against the expected new CID succeeded. A syscall trace recorded the same flock held across each generation rename and HEAD rename. The previous standalone HEAD smoke also passed after the refactor. The combined artifact SHA-256 was `f1b4e02f7a3e45427b747e9e36c75d06fe931b00328874c3d57d8984a27de928`; its guest-specific KSL1 lock was `4d2a75e45e4ad69452772ce0be468053ce095bcb82d993c540e22c5694421fc1`.

A separate test-only build paused after generation publication and before HEAD advance. SIGKILL left the old HEAD unchanged and a complete new generation. A fresh build of the uninstrumented source retried: it verified the existing generation and advanced HEAD successfully. Instrumented artifact SHA-256 `857d6d6da54f02e462ce668be886b339642a1110ff281c0620cae42b28e6b6b2`; uninstrumented retry artifact `cfb8f135625a4f4fc48811f3b8139aa785bb78909660eb726af078a2e4298c6d`. In a separate copy with an existing same-name generation whose Pack was corrupted, commit returned 107 and HEAD stayed unchanged. These are process and corruption controls, not WAL replay.

Following `sync`, a clean guest shutdown and restart changed boot ID from `82a7f5d5-b708-4e69-ad06-0a60c6298539` to `1c981289-6fa1-4e4d-9f90-b2a80422c330`; HEAD's previously recorded SHA matched and a separate Native recovery artifact parsed HEAD and verified the referenced one-byte generation. The two-Pack source was checked during the earlier transaction; this reboot recovery did not re-read that no-longer-current generation. Source-instrumentation and guest evidence are retained in task-owned scratch.

This module is not yet integrated into a product runtime. It lacks WAL, signed CID authority, durable anti-rollback, a source snapshot, hostile/distributed fencing, safe orphan cleanup and physical power-loss qualification. Cooperative locking requires all local writers to use the same stable lock inode; same-identity interference and provider traps remain possible. A guest reboot with host caches uncontrolled is not a physical disk power cut.
