# kotoba-lang/org-ietf-mls

**Messaging Layer Security — [RFC 9420](https://www.rfc-editor.org/rfc/rfc9420)
— in portable `.cljc`.** Eight of its layers so far: the array-based ratchet
tree arithmetic, the labelled cryptographic operations everything above them
is defined in terms of, the epoch key schedule, the secret tree that produces
per-message keys, PSK secrets and transcript hashes, the framing layer that
turns content into a protected message — and the ratchet tree's own node
encodings, its tree hash, and the three proposals that change its shape.

```clojure
(require '[mls.suite :as suite] '[mls.crypto :as crypto] '[mls.tree :as tree])

(def s (get suite/suites 0x0001))          ; MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519
(crypto/derive-secret s secret "epoch")
(crypto/encrypt-with-label s pk "Label" ctx plaintext eph)
(tree/direct-path 4 8)                     ; => [:ok [5 3 7]]
```

## The vectors are the working group's

Unlike ECH and ODoH, this one does not need a vendor's reference output.
`mlswg/mls-implementations` publishes the corpus every MLS implementation is
expected to agree with, and `test/mls/vectors.cljk` carries two of its files
whole, pinned by sha256 and regenerated by `scripts/extract_vectors.cljk`:

| | |
|---|---|
| `tree-math` | **10 trees**, 1 to 512 leaves — 1,023 nodes at the top end |
| `crypto-basics` | **all 7 cipher suites** |
| `key-schedule` | 7 suites × **5 chained epochs** |
| `secret-tree` | 21 trees — 7 suites × 1, 8 and 32 leaves — **287 leaves** |
| `psk_secret` | **77 entries** — 7 suites × 0 to 10 PSKs |
| `transcript-hashes` | 7 suites |
| `message-protection` | 7 suites × proposal, commit and application, both wire formats |
| `messages` | 300 entries × 14 of 17 structs, decoded and re-encoded byte for byte |
| `tree-validation` | 98 trees, all 7 suites, every node's tree hash and resolution |
| `tree-operations` | 5 — add, update and remove applied to a real tree |

**47,141 assertions on both runtimes.**

### All seven suites run

X25519, X448 and P-256/384/521 for the KEM; HKDF-SHA256/384/512; AES-128/256-GCM
and ChaCha20Poly1305. This workspace has every one of them portably, so no
suite is listed that cannot execute.

### And five of the seven sign

`SignWithLabel` and `VerifyWithLabel` run for **Ed25519** (suites 1 and 3) and
**ECDSA** over P-256/384/521 (suites 2, 5 and 7). The corpus's own signatures
verify for all five.

**Ed448 — suites 4 and 6 — has no implementation in this workspace**, so those
two refuse with `:unimplemented-signature-scheme`. A test asserts that they
refuse *by that name*, rather than skipping them: a skipped suite and a
passing one look identical in a summary line.

This section previously said none of the seven could sign. That was wrong, and
wrong in a way worth recording: `org-ietf-ed25519` is described elsewhere in
this workspace as `:clj`-only, and the claim was taken from that description
rather than from the repository. `edwards.cljc` and `scalar.cljc` have **zero
reader conditionals**, and its ClojureScript smoke test asserts signatures
byte-identical to the JVM's. The library had been portable for some time; only
the sentence about it was stale.

## The key schedule is checked as a chain, not per epoch

Each epoch's `init_secret` is the next epoch's input. The test runs the
schedule **forward** from `initial_init_secret` and never reads an epoch's
`init_secret` out of the fixture to feed the next one — an implementation that
got the chaining backwards, or recomputed each epoch from published inputs,
would pass a per-epoch check and fail this.

When an epoch does fail, the chain **stops** rather than carrying the
fixture's value forward. Continuing would let one bad epoch hide behind the
next one's inputs.

### Extract takes its salt from the top

RFC 9420's Figure 22 states this in prose above the diagram, and it is the one
thing there that is easy to invert: `Extract(salt = init_secret, ikm =
commit_secret)`, and `Extract(salt = joiner_secret, ikm = psk_secret)`.

Inverting it produces a key schedule that is **entirely self-consistent** —
every member running the same wrong code agrees with every other — and shares
nothing with anyone else. There is no way to catch that from inside; it is
what the interop corpus is for. Measured: swapping the first extract turns
385 assertions red, the second 379.

### An absent PSK is `Nh` zeros, not an empty string

The RFC writes it as `psk_secret (or 0)`, and the `0` is `KDF.Nh` bytes long.
HMAC over nothing is not HMAC over zeros, so the two give different epochs —
and a group where one member omits the field and another passes zeros will
not agree.

## The ratchet tree: encodings, hashes, and three shape changes

`mls.node` is `Credential`, `Capabilities`, `Lifetime`, `Extension`,
`LeafNode`, `KeyPackage`, `HPKECiphertext`, `UpdatePath`, `ParentNode`,
`Node` and the `ratchet_tree` extension. `mls.tree-hash` is the tree hash and
the resolution. `mls.tree-ops` applies an `Add`, `Update` or `Remove`.

With those, the `add` and `update` proposals and a Commit's `UpdatePath` —
which refused by name until now — go through.

### A codec corpus is not a semantic corpus, and they are counted apart

`messages` is 300 entries of structs another implementation serialised with
**random field values**. None of it is cryptographically valid and none of it
is meant to be: decoding those bytes and re-encoding to *the same bytes* is
agreement about the wire format and nothing more. That is exactly the
question a wire format raises, and exactly not the question a tree raises —
so `tree-validation`, which is 98 real trees with every node's hash and
resolution, is a separate corpus and a separate set of tests.

Three of the seventeen structs are the Welcome layer and nothing here reads
them. The test asserts **which** three by name rather than looping over a
handler map: a corpus that dropped a struct between releases would otherwise
produce a smaller test that still passes.

### The tree on the wire is shorter than the tree in memory

§12.4.3.3 makes both halves of this a MUST. The sender **MUST NOT** include a
blank after the last non-blank node; the receiver **MUST** check that the last
node is non-blank and then extend with blanks to a length of `2^(d+1) - 1`.

The extension is not padding for tidiness. `mls.tree`'s arithmetic derives
every parent, sibling and root from the array length — a tree left truncated
has a different root index, so every hash above the truncation point is
computed over the wrong nodes, and a perfectly valid tree comes out with the
wrong tree hash. Five entries become seven, not five, because the *leaf* count
rounds up to a power of two.

### Add is the odd one, and the corpus does not test the part that makes it odd

| | the leaf | the path to the root |
|---|---|---|
| `Add` | filled | **unmerged**, not blanked |
| `Update` | replaced | blanked |
| `Remove` | blanked | blanked, then the tree truncated |

Blanking on `Add` would throw away key material the existing members still
hold. Instead the new leaf is recorded as *unmerged* at each non-blank
ancestor, which says the true thing: those keys are known to everyone below
them **except** this leaf.

The working group's `tree-operations` corpus has two Add cases and **neither
reaches that step** — one extends into an all-blank subtree, the other's blank
leaf has no non-blank ancestor. Measured: an implementation that blanks the
path on Add passes that corpus with **nothing red**.

So the states for it come from `tree-validation` instead, which holds 63 trees
whose leftmost blank leaf does sit under a non-blank ancestor. Those trees are
another implementation's; the expected *result* is the RFC's rule rather than
another implementation's answer. That is weaker evidence and it is labelled
as such in the test rather than folded into the counts.

The `unmerged_leaves` MUST-be-sorted rule needed one step further: of those 63
states, **none** has an existing entry larger than the leaf being added, so no
state anywhere in the corpus tells the two orderings apart. That single case is
constructed, and the test says so on the line that constructs it.

### The fixture is now large enough to be worth saying so

`test/mls/tree_vectors.cljk` is 4 MB, and the ClojureScript run went from
minutes to the better part of an hour on this machine — nearly all of it in
the 98-tree corpus, evaluated by SCI. (Wall clock between launching the runner
and it reporting; the process was still inside `mls.node-test` 22 minutes in.
Not instrumented, and this machine runs a lot of other work.) That is the cost of running the working group's corpora whole rather than
sampling them. Nothing is subsampled and nothing is skipped, so the number
above is the number of assertions that ran; if that ever changes, the change
belongs in this paragraph and not in a quietly smaller count.

### A uint64 that neither runtime holds

`Lifetime.not_after` is routinely `2^64-1`. Reading it into a JVM `long`
does not give a wrong number — it throws an uncaught `ArithmeticException`;
reading it into a JavaScript number silently drops the low bits. The corpus
found this immediately, because that is what implementations actually put
there.

`Lifetime` therefore keeps its two fields as **eight-byte vectors**. Nothing
here compares them, because §7.3's lifetime check is not implemented, and a
number that cannot be trusted is a worse foundation for that check than bytes
that can.

The same read was reachable from `mls.framing/decode-private-message` with
**twelve bytes** of peer-supplied input, where the field is an epoch. Epochs go
through `mls.uint`, which refuses anything outside `[0, 2^53-1]` — narrower
than the wire format allows, and deliberate: an epoch counts commits, 2^53 of
them will not happen, and a refusal a caller can see beats a crash on one
runtime and a wrong answer on the other.

Writing that range check is where this layer's own bug was: the byte offsets
were off by two, so it would have **refused valid epochs**. A test that only
checked the too-big direction would have passed. It was caught by asserting
the accepting side of the boundary as well — `0x001FFFFFFFFFFFFF` decodes,
`0x0020000000000000` does not.

## Framing: three guarantees, and they are not the same one

A message is a `FramedContent` plus what authenticates it. Underneath sit
three separate things:

| | |
|---|---|
| the **signature** over `FramedContentTBS` | who wrote it |
| the **membership tag** over `AuthenticatedContentTBM` | the writer is in this group, this epoch |
| the **encryption** in a `PrivateMessage` | nobody outside the group can read it |

A `PublicMessage` has the first two and not the third. Dropping the second
would leave a message that anyone holding the sender's signature key could
replay into a group they had since left — which is why §6.2 makes it a MUST
for members, and why the tag is checked **before** the signature here: it is
symmetric, so it rejects most garbage before any public-key work happens.

**Application data may not travel as a PublicMessage.** §6.1 says so, and the
refusal comes before the signature step — so it holds for the Ed448 suites
too. A rule that depended on being able to sign would be no rule at all for
the suites that cannot.

### Why `mls.proposal` had to exist first

`FramedContent` embeds a Proposal or a Commit **with no length prefix**. A
reader that cannot say where a Commit ends cannot say where the signature
after it begins — so framing needs a content codec, and only `application`
(an `opaque<V>`) is self-delimiting.

`add` and `update` proposals, and a Commit's `UpdatePath`, carry `KeyPackage`
and `LeafNode` — the ratchet tree's node encodings, which are not implemented.
They refuse **by name** rather than being absent from the dispatch: *this
parser does not do that yet* and *that is not a proposal type* are different
things to tell a caller.

### The reuse guard covers four bytes

§6.3.1: XOR it over the **first four** bytes of the ratchet nonce. Not
appended, not spread over the whole nonce. It exists because the key
schedule's nonces are deterministic and a client that lost its state could
reuse a generation — and putting it anywhere else still produces a nonce, just
not one the recipient can reconstruct.

### Suites 4 and 6 are not skipped

They sign with Ed448, which this workspace does not have. Their messages are
still decoded, their content codecs still checked, and the signature step is
asserted to refuse **by that name**. A skipped suite and a passing one look
identical in a summary line.

## The transcript hash splits an AuthenticatedContent without parsing it

A Commit's `AuthenticatedContent` is
`ConfirmedTranscriptHashInput || opaque confirmation_tag<V>`, and **the
boundary is not marked**. Finding it by parsing would mean parsing a whole
Commit — proposals, an UpdatePath, a Sender — none of which exists here yet.

It does not have to be parsed. The tag is recomputable from the confirmation
key and the confirmed hash, so its encoded form is a **known suffix**: match
it, and what remains in front is exactly the input to the confirmed hash.

That is stronger than parsing, because it verifies the tag in the same step.
A content that was not produced under this key has no matching suffix, and so
does a content that is not a Commit — those are not distinguished, and
deliberately so: from outside, both are the same statement.

Epoch 0's interim hash is the **empty string** — not a hash of nothing, and
not `Nh` zeros. A group started from any other value agrees with no one, and
the difference never shows up inside that group.

## PSKs are chained, and the order is inside the derivation

`psk_secret_[i] = Extract(psk_input_[i-1], psk_secret_[i-1])`, from `Nh`
zeros. Each PSK is expanded with a `PSKLabel` carrying its **index and the
total count**, so the same set in a different order is a different secret, and
a subset is a different secret again.

That is what stops a member from quietly dropping a PSK it does not hold and
proceeding with the rest. §8.4 requires existing and new members to indicate
the same PSKs in the same order; this is the mechanism that makes a
disagreement visible instead of silent.

With no PSKs the answer is `Nh` zeros — the same value the key schedule
substitutes when the field is absent. The two paths are asserted to agree,
rather than both happening to be written the same way.

## The secret tree, and why generation 15 is the useful one

`encryption_secret` sits at the root of a tree with the **same shape as the
group's ratchet tree**. Each member owns its own leaf and runs two hash
ratchets from it — one for handshake messages, one for application messages —
producing a single-use key and nonce per message.

Only the path from root to leaf is walked. Materialising the tree would
compute every other member's secrets as a side effect of finding one's own,
which is the thing the shape exists to avoid.

**A ratchet is a hash chain, so generation 15 costs fifteen derivations.** An
implementation that used the generation only as a context — deriving
generation 15 straight from the root — would agree at generation 0 and
diverge everywhere after. Generation 0 alone is what a corpus without a
second entry would check; this one has both, and the difference is asserted
directly.

### Siblings are told apart by the context, not the label

Both children of a node derive with label `"tree"`. What distinguishes them
is the **context**: `"left"` or `"right"`. Swapping the two roles makes
siblings equal, and every member of the group holds every other member's
keys. Measured: 2,240 assertions red either way.

### Sender data is bound to the ciphertext it describes

Its key and nonce come from `sender_data_secret` and a **sample of the
message** — the first `KDF.Nh` bytes, or the whole thing if it is shorter. A
message shorter than `Nh` is ordinary, not an edge case: replacing `take` with
an index that assumes the length throws on exactly those.

## The nulls are the interesting half of tree-math

For each tree the corpus publishes the full `left`, `right`, `parent` and
`sibling` arrays with `null` where the operation has no answer — a leaf has no
children, the root has no parent. An implementation returning `0` or the node
itself for those would agree with the corpus **everywhere else**, so they are
asserted as errors with their own reasons.

Whether a node is the root depends on how many leaves the tree has: node 7 is
the root of an 8-leaf tree and an ordinary parent in a 16-leaf one. Both are
checked.

## RefHash and KDFLabel are hashes of length-prefixed values

Which is why `mls.varint` is its own namespace with its own tests. RFC 9420
§2.1.2 differs from QUIC's variable-length integers (RFC 9000 §16) in exactly
one way: it **requires** the smallest encoding and says a decoder MUST reject
a longer one.

That is not tidiness. These lengths prefix values that get hashed, so two
encodings of one length would be two byte strings for one object — two
`KeyPackageRef`s for one KeyPackage, and a signature that verifies over one
and not the other.

### Two things a round-trip cannot see

**The `"MLS 1.0 "` prefix.** It separates MLS from any other protocol that
labels KDF inputs the same way, and both halves of every operation here are in
this repository — so dropping it would leave any self-consistency check green.
It is checked against the serialised `KDFLabel` and `EncryptContext` directly.

**The two signature encodings.** RFC 9420 §5.1.2 says EdDSA is `R || S` and
ECDSA is DER, and they are not interchangeable — a library that produced one
where the other was expected would produce something no peer accepts. The
corpus's own signatures are 64 bytes for suite 1 and a DER SEQUENCE for suite
2, and a test says so.

**The generation's width.** `DeriveTreeSecret` uses a big-endian uint32, and
the corpus's own generation is `0xA0A0A0A0` — symmetric in every byte, so it
would pass with the bytes reversed. Values that are not symmetric are checked
against `ExpandWithLabel` called directly.

### A label that looks like hex, and is not

`MLS-Exporter`'s label in the corpus is a 64-character string of hex digits.
It was read as hex — 32 bytes — and on the strength of that reading
`mls.crypto/labelled` was generalised to accept raw bytes as well as strings.

It is a **label that happens to look like hex**, passed as text. The wrong
reading produces a plausible, wrong secret for every one of the 35 exporter
cases, which is how it was caught. The generalisation ran fine and was needed
by nothing, so it is gone: an unexercised branch justified by a misreading is
two problems at once.

### Reading the labels back rather than building them

The tests compare the *decoded string* to `"MLS 1.0 Test"` instead of building
the expected bytes with `(map int "MLS 1.0 Test")`. That expression is code
points on the JVM and a vector of **zeros** under ClojureScript, and this test
walked into it — the **fourth time in one afternoon**, across four namespaces,
each written by someone who had just been bitten by it. `(map char bytes)` is
correct on both, so the comparison happens on the side with no trap.

## Not here

MLS is large and this is eight layers of it. Still to come: parent hashes,
TreeKEM, and Welcome.

Parent hashes are next. Everything needed for them is now here — the node
encodings, the tree hash, the resolution — and they are what makes a tree
*authenticated* rather than merely agreed on: the tree hash says the group
holds the same tree, and the parent hash says each node's key was actually
put there by someone entitled to.
