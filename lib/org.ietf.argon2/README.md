# kotoba-lang/org-ietf-argon2

**[RFC 9106](https://www.rfc-editor.org/rfc/rfc9106) Argon2 — Argon2d,
Argon2i and Argon2id — in portable `.cljc`.**

`kotoba-lang/pqh` names the suite `argon2id-v1`, defines an `IKdf` capability
for it, and says in its own docstring that no Argon2id math lives there: a
host must inject BouncyCastle on the JVM or `@noble/hashes` under
ClojureScript. That is a reasonable seam and a real gap — there was no
in-language implementation to serve as the reference a provider is checked
against, and none at all on a host that has neither.

## Read this first

**This is a correct reference implementation, not a fast one.** Measured on
one workstation at load average 66, best of three runs:

| parameters | JVM | nbb (ClojureScript) |
|---|---|---|
| m=32 KiB, t=3 | 40 ms | 142 ms |
| m=1 MiB, t=1 | 183 ms | 1.2 s |
| m=8 MiB, t=3 | 4.0 s | 27 s |
| **m=19 MiB, t=2** (OWASP minimum) | **7.1 s** | **41 s** |

A vetted native provider does the last row in well under a tenth of a second.
So:

- **Do not put this on an interactive login path at recommended parameters.**
  Where a native provider exists, use it — that is what `pqh`'s capability
  seam is for, and this library does not replace it.
- **Do use it as the oracle that provider is checked against**, as the
  in-language implementation on a host that has no provider, and at the
  smaller parameters that suit key derivation from an already-strong secret
  rather than from a password.

Measure at your own parameters on your own runtime before deciding. The
numbers above are one machine on one day and are not a promise.

## Use

```clojure
(require '[argon2.core :as a])

(a/argon2! {:password (a/utf8 "correct horse battery staple")
            :salt     (a/utf8 "sixteen bytes!!!")
            :memory-kib 19456 :iterations 2 :parallelism 1 :tag-length 32})
;=> [0xb7 0xf3 …]   a vector of ints 0..255

(a/hex (a/argon2! …))   ;=> "b7f32b13…"
```

| option | default | |
|---|---|---|
| `:type` | `:argon2id` | also `:argon2d`, `:argon2i` |
| `:password` | — | required |
| `:salt` | — | required, ≥ 8 bytes |
| `:secret` | — | RFC 9106's **K**: a key the verifier holds and the stored hash does not reveal |
| `:associated-data` | — | RFC 9106's **X** |
| `:parallelism` | 1 | lanes |
| `:memory-kib` | 19456 | rounded **down** to a multiple of `4p`, per §3.1 |
| `:iterations` | 2 | |
| `:tag-length` | 32 | ≥ 4 |

`argon2` returns `{:status :ok :tag […]}` or `{:status :error :reason kw}`;
`argon2!` throws instead. The reason keywords — `:salt-too-short`,
`:tag-too-short`, `:memory-too-small`, `:iterations-too-few`,
`:parallelism-out-of-range`, `:unknown-type` — are contract.

**`utf8` is part of the API on purpose.** A password is almost always a
string, and the obvious translation is wrong on one runtime in a way that
produces a plausible answer rather than an error: `(mapv int "Password")`
gives code points on the JVM and a vector of **zeros** under ClojureScript,
where a character is a one-character string. Two different passwords then
hash identically. This library's own test suite hit exactly that, and only
the ClojureScript runner saw it.

## Verify

```sh
kbb -M:test                                                        # JVM
kbb --backend sci --classpath "$(kbb -A:cljs -Spath)" scripts/verify-cljs.cljk   # ClojureScript
kbb -M:oracle                                                      # + differential vs BouncyCastle
```

Three layers, and each answers something the others cannot.

**Known answers.** RFC 9106 §5.1–5.3 verbatim, covering all three variants
with a secret and associated data supplied; plus two vectors from
`kotoba-lang/pqh`, recorded there as verified byte-identical against
`@noble/hashes`, which use the OWASP-recommended parameters the RFC's 32 KiB
vectors do not. **All five were reproduced with BouncyCastle 1.78.1 before
this implementation was written**, so the oracle existed before the code did
rather than being fitted to it.

**Differential.** `kbb -M:oracle` runs 150 comparisons against
BouncyCastle across three variants, nine parameter sets and five tag lengths,
with secrets and associated data varied. Five vectors pin three variants at
two parameter sets; that leaves untested exactly where Argon2's indexing
branches — the reference-area size has four cases, the slice boundary behaves
differently at index 0, multi-lane runs reach cross-lane references that p=1
never does, and the second pass XORs where the first overwrites. The
parameter spread is generated by a fixed LCG, not a random source: a
differential test that picks new inputs each run reports failures nobody can
reproduce.

BouncyCastle is scoped to the `:oracle` alias and never appears in `:deps`.
It is what this library is *checked against*, not something it builds on.
`kotoba-lang/pqh` scopes its own Argon2 fixture the same way.

**Both runtimes.** Every 64-bit operation is a different instruction sequence
on each: the JVM's `int-array` is signed and needs a mask on read, a
`Uint32Array` does not; JavaScript's shift count is taken mod 32 so `<< 32` is
silently `<< 0`; and `mul32` exists because a 32×32 product is exact in
neither a JavaScript number nor a 32-bit operator.

Reintroducing a one-bit error — rotating by 62 instead of 63 in the mixing
step — turns 140 of the 150 differential comparisons red. That was measured,
not assumed.

## How the 64-bit arithmetic is done, and why not the other way

`org-ietf-blake2` makes a word a `long` on the JVM and a `BigInt` under
ClojureScript, and says in its own docstring that hashing a large file on the
JavaScript side would be too slow. **Argon2 is the large file**: at 19 MiB it
performs about 39,000 block compressions, each eight rounds of eight mixing
steps. BigInt allocates on every operation, so that representation is not
merely slower here — it is the difference between seconds and hours.

So a word here is two ordinary integers in `0 .. 2^32-1`, held in a flat array
of 32-bit lanes that both runtimes have a fast version of. All of it is
confined to `argon2.u32`; everything above is a single code path. The
arithmetic never allocates: an earlier draft returned `[hi lo]` vectors and
made about five million of them per hash.

BLAKE2b itself *is* taken from `org-ietf-blake2` — it runs 62 times per hash,
not five million, and two copies of a hash function is how they drift.

## Not here

**Argon2 version 0x10.** It differs from 0x13 in the second-pass rule
(overwrite where 0x13 XORs). Supporting a variant nothing here produces would
be a second code path nothing here tests.

**Threads.** `:parallelism` is the RFC's `p` and is honoured exactly — the
lanes, slices and synchronisation points are all computed — but the segments
run sequentially. The output is identical either way; that is what the sync
points are for. Parallel execution would need a threading capability, which a
portable `.cljc` leaf does not have and should not acquire.
