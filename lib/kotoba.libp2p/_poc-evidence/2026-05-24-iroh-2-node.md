## Interpretation

- iroh nodes auto-discover via the n0 relay + DHT (no DNS dependency).
- NodeId is Ed25519, bit-isomorphic to libp2p PeerId and the `did:key`
  form — same key material as ADR-2605241800 §D1 declares for the
  primary libp2p Multiaddr.
- iroh's wire-level "ticket" is a self-contained dial address; for our
  ADR-2605241800 use case, the agent.json `service[]` carries the
  NodeId only (`iroh://<NodeId>`) and the dialer relies on standard
  iroh discovery to resolve to a reachable address.

## Limitations vs libp2p (per ADR-2605241800 §Alternatives)

- iroh-cli does **not** ship an `ipfs p2p`-style listen/forward TCP
  tunnel. XRPC tunneling via iroh requires a small Rust binary using
  the `iroh` crate's `Endpoint::connect` + custom protocol — deferred
  to a follow-on PoC.
- iroh's relay quorum semantics (multiple n0-operated relays) are
  serviceable today; self-hosted relay for the religious-corp is a
  Phase D consideration per ADR-2605241800.

## Conclusion

iroh works as a wire-compatible sibling to libp2p for Ed25519-keyed
peer-to-peer byte transfer. ADR-2605241800 §L2 (Transport) confirmed:
**libp2p is primary, iroh is experimental sibling**, both share the
same Ed25519 NodeId identity, both can be declared inside the same
agent.json `service[]` array.
