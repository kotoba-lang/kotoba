# ADR-0064 — A tripwire that fails on good news

Date: 2026-08-18

## Status

Accepted and executable. It closes the hole ADR-0063 named in its own
"remaining boundary": if the upstream answer arrives, no gate notices.

## Context

`:test-fleet` drops one test via `^:upstream-blocked`, and that exclusion rests
on exactly one fact — **nothing in the value runtime compiles**, because it
needs an intrinsic (amu#625) and an export answer (#626) this repository does
not own.

Facts like that stop being true without telling anyone. The moment one does,
the exclusion becomes what this series has repeatedly called decoration: a gate
quietly not looking at something it could now see, with nobody assigned to
notice. ADR-0063 wrote *"whoever removes the metadata should be the person who
reads #625 closing"* — which is an assignment to a person who may never read it.

## Decision

**A tripwire that fails when the value runtime starts working.**
`the-upstream-exclusion-is-still-justified` reads the receipt and requires
`passing = 0`.

It is the only assertion in this repository that fails on good news, and its
message is a runbook rather than a complaint: re-run the verifier, wire the
objects that now build into a build script, remove the metadata, drop the
`-e :upstream-blocked` from the alias, raise `passing-floor`, delete the
assertion.

`passing-floor` bounds the same number from below — passing may only increase.
This bounds it from above. **The day the two disagree is the day the exclusion
must be revisited, and the disagreement is the alarm.**

The tripwire runs in `:test-fleet` too, so the *fleet* goes red on that day.
That is deliberate: a red requiring a five-line change is worth having, and it
is the opposite of the unfixable red this series has spent fourteen iterations
refusing to add.

## Executable evidence

`aiueos.value-runtime-baseline-test`: **13 tests, 84 assertions, 0 failures**.
`kbb -M:test-fleet`: **632 tests, 9340 assertions, 0 failures.**
`kbb -M:test`: 633 / 9412 / 12, unchanged.

**Both directions**: editing the receipt to claim two objects pass fires the
tripwire with the full runbook — and also fires `the-failure-count-has-not-grown`
and `the-causes-account-for-every-failure`, because a hand-edited receipt is
internally inconsistent. Three assertions catching one lie from three
directions is the receipt's integrity checks working, not noise.

## Remaining boundary

- **It watches compilation, not builds.** The excluded test is about objects
  being *built by a script*; the receipt is about them *compiling*. Compiling
  is the necessary condition, so it trips first — but someone still has to wire
  the build, and nothing checks that they did beyond the excluded test itself
  once the metadata comes off.
- It cannot fire if nobody re-runs the verifier: the receipt is regenerated by
  hand. A stale receipt keeps claiming eleven failures forever, and the only
  thing standing against that is the compiler-sha assertion from ADR-0059.
