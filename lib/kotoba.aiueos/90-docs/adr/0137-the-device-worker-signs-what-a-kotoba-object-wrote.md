# ADR-0137 — The device worker signs what a Kotoba object wrote, and it can speak v3

Status: accepted
Date: 2026-09-02
Supersedes: nothing. Extends ADR-0015 (the honest C boundary) to the Murakumo
device-P256 worker client, which was one of the last C files in the kernel that
made a claim rather than moving a register.

## The decision

`kotoba_aiueos_device_worker_canonical` writes the text the K16 device hashes
and signs. `kernel/device_result.c` fills a 576-byte fixed-layout record and
calls it; it no longer decides field order, decimal rendering or sentinels.

The object writes protocol 2 **and** protocol 3 — the token-array protocol that
went live on api.murakumo.cloud on 2026-09-02 (cloud-murakumo-api `394f983`,
worker version `2c7fbc3a`, spec `docs/device-worker-v3.md`). The C still only
*asks* for protocol 2; the v3 half of the object is exercised by its contract
and by the boot self-test, not by a live request. That gap is stated below
rather than papered over.

## Why this was not mechanism

ADR-0015 draws the C boundary at mechanism: C owns registers, MMIO, the GDT,
paging and sockets, and the judgements are compiled Kotoba. A canonical text is
not a register. It is the sentence the device asserts about itself, and the only
thing a verifier can say about a sentence it did not reconstruct is that the
signature did not verify. So every mistake in this file — a field in the wrong
order, a decimal that lost its high digits, a sentinel the server did not
expect — surfaces at the server as *the signature is bad*, naming the wrong
cause. That is the worst failure mode a decision can have, and it is why this
one had to move.

There is a second, sharper reason, and it is specific to v3. The server's rule
is `protocol 3 poll/control must not carry a job output`. A device that copied a
stale digest out of its own context would sign a poll that settles a job — and
no clause on the device side would have fired, because in C the sentinel was
something the caller passed in. **The object writes the sentinels rather than
reading them.** For a poll and a control-ack it never reads offsets 368, 432,
104 or 2 at all. The vector
`:worker-poll-v3-with-a-stale-digest-in-the-context` is that argument made
executable: it supplies a real result's two digests and its count, and expects
the sentinel text byte for byte.

## The interface, and why it is not a boolean

    (aiueos-device-worker-canonical ctx ctx-len out out-cap)

      > 0   the number of canonical bytes written into `out`
     -1     ctx-len below 576
     -2     out-cap below 1024
     -3     protocol is neither 2 nor 3
     -4     operation is not poll (1), result (2) or control-ack (3)
     -5     the stop-reason byte is not the one this protocol and operation
            admit
     -6     a numeric slot at or above 2^56
     -7     protocol 2 carrying a protocol 3 field
        0   is never returned

This is the `aiueos-qwen35-*` convention rather than `aiueos-aes128-gcm`'s
zero-is-success one, and the reason those three objects give applies here
unchanged: the useful answer is a **length**, and a length cannot share a
non-negative value space with a reason code. A caller writing
`if (canonical(...))` would accept exactly the contexts this refuses.

The layout is in `os/aiueos/contracts/device-worker-canonical-v1.edn` `:ctx` and
in `kernel/device_result.h` as `AIUEOS_DWC_*`. It is in the header rather than
inside `device_result.c` because **two** translation units fill one of these
records — that function and the boot self-test in `main.c` — and a second
literal copy of the offsets is exactly the drift the macros avoid.

## Two things this object cannot do, and what it does instead

**No string literals.** `bytes-literal` answers with the *address* of bytes the
backend placed in an image, and a kernel `.o` is not an image; there is no other
way to name a byte string in this subset. The seven fixed words live in one
generated character table addressed by `(offset, length)`. Generated by
`os/aiueos/scripts/gen-device-literal-pool.cljk` from
`os/aiueos/kotoba/device-worker-canonical-pool.txt` rather than transcribed: 58
nested `if` arms written by hand is the shape where one wrong ASCII code becomes
a signature refused for the wrong reason.

**No helper may take more than five parameters.** Measured 2026-09-02:
`:kotoba.error/max-parameters` applies to every `defn`, not only to the exported
entry. A byte copier that carried both window lengths as parameters is six, so
the two window lengths are **literals** — 576 for `ctx` and 1024 for `out` — and
the declared sizes are checked against them before a byte is read. The
consequence is a constraint on the C: it must allocate exactly those sizes, or
the bounds check is measuring the wrong region.

`DEVICE_CANONICAL_MAX` grew from 512 to 1024 for this. The widest protocol 3
result is 716 bytes and the old ceiling would have silently refused it — the C's
`bounded_buffer` sets `ok = 0` and the request is dropped, which on a device
that is polling looks like a network problem.

## What was verified, and by what

**The interpreter, against two other implementations.**
`os/aiueos/scripts/verify-admissions.cljk` grew a builder for this format and
runs the contract through `kir/execute` with a real memory image:

    vectors=16 traps=0 memory=7
    observed=-7,-6,-5,-4,-3,-2,-1,328,350,367,382,463,518

All seven reason codes are produced by a vector that names the clause. The
expected bytes come from two places, deliberately different:

| protocol | oracle |
|---|---|
| 2 | `os/aiueos/tests/device_result_v2_model.c --dump-canonical` — the C writer this ADR deletes, captured through that model's `kotoba_aiueos_sha256` stub, which records the exact bytes the C was about to hash |
| 3 | the worked example in network-awai/cloud-murakumo-api `docs/device-worker-v3.md`, pinned there by `v3-canonical-is-the-v2-list-plus-four-fields-then-the-nonce` — the **server** that will verify what this device signs |

**Discrimination, shown rather than asserted.** Two deliberate breaks:

- `put-v3` made to *read* the context digests on a poll instead of writing the
  sentinels → red on `:worker-poll-v3-with-a-stale-digest-in-the-context`,
  region `:canonical`, and **only** on that vector. The plain poll's context
  already holds sentinels, so it cannot tell; that is why the third vector
  exists.
- `decode-cycles` and `inference-cycles` swapped in the field order → red on
  `:worker-result-v2`, region `:canonical`.

Restored unchanged: green, same 16 vectors and 7 memory assertions.

**The CPU, under QEMU.** The interpreter agreeing with these bytes says nothing
about what the backend emitted. `DEVCLIENT-PARITY canonical ok` on the debug
console is the emitted object running on x86-64: a protocol 2 result against the
C's own bytes, the protocol 3 worked example, and one refusal (-7), so a run
that never saw the object say no is not counted as a pass.

**The host, after the flip.** `smoke-device-result-v2.sh` still passes, and it
is now a genuine parity check rather than a stub: the model supplies
`kotoba_aiueos_device_worker_canonical` with the **old C writer**, so the test
proves the 576-byte record `device_result.c` fills denotes the same text the C
used to write from the same struct. `--dump-canonical` produces byte-identical
output before and after the flip.

## What this does NOT do

- **The device still speaks protocol 2 on the wire.** The object can write v3;
  `device_result.c` sets `worker_ctx[AIUEOS_DWC_PROTOCOL] = 2` and the JSON body
  still says `"protocol":2`. Advertising `:qwen38-generate`, parsing a
  `qwen38-generate` job and settling one are the remaining stages.
- **Nothing here was exercised against real K16 hardware**, and no live request
  was sent. QEMU is not a K16 node.
- **`device-worker-digest`, `device-worker-body` and `device-worker-parse` do
  not exist.** The last two have export symbols and fuel tiers reserved in
  kotoba-native#117; the first does not, deliberately — an allowlist row for an
  object nobody has written is a claim. See *Resume* below.
- **The fuel tier is COMPUTED, not measured.** 65,536 against ~2,400 charged
  calls, derived in kotoba-native `elf64.cljc`'s `device-client-fuel?` arm. The
  object returns under QEMU, which is evidence the bound is not too small; it is
  not a measurement of what it actually costs.
- **kotoba-native#117's comment cites "aiueos ADR-0136".** This ADR is 0137;
  0136 was taken by another stream between that PR being written and this one
  landing. Recorded rather than force-pushed.

## Resume

1. `device-worker-parse`: a bounded, refuse-on-unknown walker over the poll
   response (`accepted`, `operation`, `ready`, `control`, `job` null or
   `{job-id, kind, input {tokens[], max-tokens, stop-tokens[]}, input-sha256}`)
   into a fixed-layout record plus a token region. Refuse above 8,192 response
   bytes; refuse a token at or above 248,320. Symbol and 10,000,000 tier already
   reserved.
2. `device-worker-body`: the JSON for poll / result / control-ack, with
   `:output-tokens` bounded in the object at 384 ids so the buffer stays 4,096.
   Symbol and 65,536 tier already reserved.
3. `device-worker-digest`: `input-sha256` / `output-sha256` over the token
   array. **This one needs a new shared module before it can be written.**
   `aiueos/lib/sha256_core` hashes at most 192 bytes out of the caller's own
   context; the input canonical form is `4 * (count + 2)` bytes and the protocol
   allows 32,768 tokens, which is 131,076. The shape that fits the five-parameter
   ABI is a *streaming* core — `sha-init` / `sha-block` / `sha-emit` over a
   64-byte block slot, with the caller synthesising `be32(count) || be32(t_i)…
   || be32(max-tokens)` a block at a time. Even then the token region is capped
   by the widest window primitive (65,536 bytes = 16,383 tokens), so reaching the
   protocol's 32,768 needs `kernel-subregion` re-basing. Write the module first;
   do not widen `sha256_core`'s literal 800-byte window to do it.
4. Then the wire flip: advertise `:qwen38-generate`, alternate the signed
   `:protocol` per poll, and refuse a v3 job that carries tokens with
   `stop-reason error` until the Qwen kernels and tokenizer can settle one.
